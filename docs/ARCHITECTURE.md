# Architecture Design — CPU and Memory Stress Testing Tool

## 1. Overview
A 3-layer web application:

```
┌────────────────────┐      HTTP + SSE       ┌────────────────────┐
│  Frontend          │ ◄────────────────────► │  Backend           │
│  React + Vite      │  REST + Server-Sent     │  Node + Express    │
│  Dashboard UI      │  Events                │  API + Engine      │
└────────────────────┘                        └────────┬───────────┘
                                                       │
                                              ┌────────▼───────────┐
                                              │  Stress Engine     │
                                              │  worker_threads +  │
                                              │  controlled alloc  │
                                              └────────┬───────────┘
                                                       │
                                              ┌────────▼───────────┐
                                              │  Metrics + Store   │
                                              │  os module (1s) +  │
                                              │  SQLite run history│
                                              └────────────────────┘
```

The frontend never stresses the browser itself. All load is generated by the backend process on the host machine, so measurements reflect the real OS.

## 2. Components

### 2.1 Frontend — `frontend/` (React + Vite)
- **Control Panel** — form for CPU workers, CPU intensity %, memory MB, memory pattern, duration, load pattern.
- **Live Dashboard** — CPU %, per-core bars, memory used/free, swap, load avg, throughput. Small minimal charts (SVG), updated via SSE every 1s.
- **Run History** — table of past runs (config + peak / avg metrics + status).
- **Compare View** — pick two runs, overlay their CPU/memory curves.
- **Safety UI** — prominent STOP button, status badge (idle / running / stopping), guardrail warnings.
- State: React only, no global store needed. `fetch` for REST, `EventSource` for SSE.

### 2.2 Backend — `backend/` (Node + Express)
| Module | File | Responsibility |
|---|---|---|
| Server | `src/server.js` | Express app, CORS, JSON, static wiring, port 4000 |
| Routes — System | `src/routes/system.js` | `GET /api/system` — CPU model, cores, total/free memory, OS, load avg |
| Routes — Runs | `src/routes/runs.js` | `POST /api/runs`, `GET /api/runs`, `GET /api/runs/:id`, `POST /api/runs/:id/stop`, `GET /api/runs/:id/stream` (SSE), `GET /api/runs/:id/export` |
| Stress Engine | `src/lib/stressEngine.js` | Owns one active run. Spawns / stops workers, enforces caps, watchdog. |
| Metrics | `src/lib/metrics.js` | Samples `os.cpus()`, `os.freemem()`, `os.totalmem()`, `os.loadavg()` every 1s. Computes CPU % from tick deltas. |
| Store | `src/lib/store.js` | SQLite via Node's built-in `node:sqlite`. Tables: `runs`, `samples` (samples carry `per_core_json`). |
| CPU Worker | `src/workers/cpuWorker.js` | `worker_threads` worker. Busy-loop with duty-cycle sleep to hit target intensity %. Reports ops/sec via parentPort. |
| Memory Worker | `src/workers/memoryWorker.js` | Allocates `Buffer`s of configured size, touches pages (writes every 4KB), supports hold / churn patterns. |

### 2.3 Data Model (SQLite)
```sql
runs(id, created_at, status, config_json,
     cpu_workers, cpu_intensity, memory_mb, memory_pattern,
     duration_sec, load_pattern,
     avg_cpu, peak_cpu, avg_mem_pct, peak_mem_pct, ops_total, end_reason)

samples(id, run_id, t_sec, cpu_pct, mem_used_mb, mem_pct,
        swap_used_mb, load1, ops_per_sec, per_core_json)
```

## 3. API Contract (Phase 1 — frozen)

```
GET  /api/health            → { status: "ok", uptimeSec }
GET  /api/system            → { cpu: { model, cores, speedMHz }, memory: { totalMB, freeMB }, os: { platform, release, arch }, loadAvg: [1,5,15] }
POST /api/runs              → { runId }   body: { cpuWorkers, cpuIntensity, memoryMB, memoryPattern, durationSec, loadPattern }
GET  /api/runs              → [ { id, createdAt, status, config, avgCpu, peakCpu, ... } ]
GET  /api/runs/:id          → { run, samples: [...] }
POST /api/runs/:id/stop     → { status: "stopped" }
GET  /api/runs/:id/stream   → SSE: { t, cpuPct, memUsedMB, memPct, load1, opsPerSec } every 1s
GET  /api/runs/:id/export   → CSV download
```

Status values: `running` | `completed` | `stopped` | `failed` | `auto-stopped`.

## 4. Key Design Decisions

1. **Node + worker_threads (not child processes) for CPU.** Threads share the process, start fast, and can be terminated cleanly with `worker.terminate()`. One worker per requested CPU core, each with its own duty cycle.
2. **Duty-cycle intensity.** To hit e.g. 50% intensity, a worker busy-loops for 50ms then sleeps 50ms in a 100ms window. This gives predictable average load without pegging the core.
3. **Memory via Buffers + page-touching.** Allocating alone does not pressure RAM (lazy pages). The worker writes 1 byte per 4KB page so the OS actually commits the pages.
4. **SSE (not WebSockets) for live metrics.** One-way server → browser stream is all we need, simpler than sockets, auto-reconnects.
5. **Single active run.** Only one stress run at a time. This keeps measurements interpretable and prevents accidental double-load. A new run is rejected while one is running.
6. **Caps + watchdog (safety).** Backend enforces: `memoryMB ≤ 50% of total RAM`, `cpuWorkers ≤ cores`, `durationSec ≤ 600`. A watchdog samples every 1s and auto-stops if free memory < 120 MB or memory use > 97%. Absolute thresholds (not % free) — a host may already sit at 85–90% used, so a relative threshold would false-trigger. CPU 100% is intentional and does not auto-stop.
7. **SQLite for history.** Zero-setup, file-based, enough for a lab tool. No MySQL server needed to demo. Implemented with Node's built-in `node:sqlite` (no native dependency), DB at `backend/data/stress.db` (gitignored).

## 5. Load Patterns (Phase 2)
- **Sustained** — constant intensity for the whole duration.
- **Ramp** — intensity rises linearly from 0 to target over the duration.
- **Spike** — baseline 10% with a 10-second burst to target in the middle.
- **Step** — intensity jumps in 3 equal steps.

## 6. OS Concepts Demonstrated
- CPU scheduling / multi-core parallelism / duty cycle
- Memory allocation, page-touching, RSS vs virtual memory
- Swap / paging and thrashing (visible when memory pressure is high)
- Load average vs CPU % (why load can exceed core count)
- Resource limits, watchdog, graceful termination

## 7. Security / Safety Notes
- Local lab tool — bind to `localhost` by default, do not expose publicly without auth.
- Never allocate unbounded memory; all allocations go through the capped engine.
- All worker termination paths (STOP, auto-stop, duration end, server shutdown) are tested in Phase 5.
